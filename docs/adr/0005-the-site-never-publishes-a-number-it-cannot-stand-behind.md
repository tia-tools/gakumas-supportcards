# The site never publishes a number it cannot stand behind; an unscoreable card is hidden and a person is asked

To let the weekly data update run unattended, the agent proposed publishing an effect the pipeline cannot count as 0 with a visible flag. The user rejected it: a placeholder number, flagged or not, breaks the tool's trustworthiness, whereas a missing card is an honest absence. So an effect that cannot be counted is never published as any number; the card carrying it is hidden from the table while every other card in the same update publishes normally, and the open question reaches the user as a conditional pull-request approval carrying a proposal — the routine part of an update merges and deploys by itself, only the held part waits. The approval is meant to arrive as a push notification with an in-place approve button (Discord first), served by a separate reusable service; until that exists, approving means merging the pull request on GitHub. Alternatives rejected: a flagged zero (above); blocking the whole update until a person acts (one unknown effect on one card would hold back every other new card); showing the card with 確認中 in place of numbers (the user chose hidden).

Source: user decisions D33 and D34, sessions of 2026-09-20 and 2026-09-21 (`docs/plans/EXECPLAN_SUPPORT_CARD_SCORE_TABLE.md` § Decision Log). The approval service is not designed yet.

Addendum 2026-09-22 (status unchanged, the hiding half implemented): `bun run generate` lists held cards with their reasons in `data/held.generated.ts` and the page leaves them out (`docs/plans/EXECPLAN_COUNTING_MODEL.md`, Milestones 1 and 4). A card is held for one of two kinds of reason: an effect the pipeline cannot read — a trigger piece of unknown kind, an unknown `for_` scenario token, an effect type that is neither a parameter type nor audited as non-parameter — or an effect it can read but no shipped route profile has a number for — a phase type no profile counts, a never-seen member of a filter family without a default (same plan, decisions C4, C5, C12, C17, C20). Schema errors, unknown enum values, dangling ids and a drop in the card count still stop the run, because they mean the upstream dump is broken rather than that the game grew. The conditional pull request and the approval service are still to come, with Milestone 5 of `docs/plans/EXECPLAN_SUPPORT_CARD_SCORE_TABLE.md`.
