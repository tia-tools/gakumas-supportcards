# Published scores are committed as a snapshot, and a data update may not move a score whose card did not change

For the weekly data update to publish without a person reading its diff, something has to notice when a number moves that should not have. `bun run generate` therefore writes `data/scores.generated.json` — for every card that is not held, a hash of its generated record and its 点数 at 凸0–4 under every shipped route profile — and the file is committed like the rest of the generated data. `scripts/check-score-stability.ts` recomputes the scores from the working tree and compares them with the snapshot committed at a git ref: a card whose hash is unchanged must score exactly the same under every profile; new, removed and newly held cards are free to differ; a stale snapshot in the working tree fails too. A deliberate change of a route profile or of the engine fails the check by design and is resolved by a person reviewing the listed moves and committing the regenerated snapshot. Alternatives rejected: comparing the old and the new card data under the current engine and profiles, which the plan first asked for, is vacuous, because the same engine and profile can never score an unchanged card differently; checking out and running the code of the base commit pins the check to old engine interfaces and cannot replay across a refactor. Known blind spot: a parser change that reads an unchanged trigger id differently also changes the card's generated record, hence its hash, and passes; the parser's unit tests and the golden scores over frozen cards (`data/scenarios/golden.test.ts`) cover that side.

Addendum 2026-09-29 (status unchanged, what is pinned refined): the snapshot no longer stores folded totals. Per card it stores the flat points (skills, events, items) under every route profile *and every lesson-split preset*, and the パラメータボーナス+ permil per 凸 — the parts a data update can move — and the bonus base, a modelling parameter with a player input since ADR 0001's addendum of the same day, is applied when a score is read. A base or default-share change therefore leaves the file untouched, while an unattended move in flat points or permil still fails the check; the former format is rejected by name. Per preset rather than under the total-best preset because a base change could flip which preset wins and move a card's recorded flat points without any data change (found by a Codex review).
