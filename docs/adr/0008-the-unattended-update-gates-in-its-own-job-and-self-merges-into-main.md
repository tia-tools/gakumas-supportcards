# The unattended data update runs its gates in its own job, publishes through a self-merged pull request into `main`, and deploys by calling the deploy workflow

`main` is production and `develop` is development, and the daily data update is the one change that enters `main` directly: GitHub runs scheduled workflows only from the default branch, so with `main` as production the update's workflow file and the code it runs are the same version and its merge lands on the branch that deploys; it then merges `main` back into `develop` (a conflict becomes a pull request, never a forced merge). A pull request opened or merged with the built-in `GITHUB_TOKEN` triggers no workflows, so the update cannot rely on checks on its pull request or on the push its merge makes: the tests, type check, lint and score-stability check (ADR 0006) run inside the update job before any pull request exists, the pull request is opened and immediately merged with a merge commit as the audit trail (a review requirement on `main` makes that merge fail and leaves it for a person, the intended fallback), and `update-data.yml` calls `deploy.yml` itself through `workflow_call`. Rejected: a separate `prod` branch (the schedule would run `main`'s workflow against `prod`'s code), a personal token or GitHub App so the bot's pull request gets checks (a long-lived credential for no extra safety, since the same gates already ran), third-party pull-request actions (supply chain for what four `gh` commands do). Anyone "simplifying" this by moving the gates onto the pull request, or by dropping the explicit deploy call, silently turns them off.
