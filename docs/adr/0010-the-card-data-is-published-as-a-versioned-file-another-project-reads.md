# The card data is published as a versioned file another project reads at runtime, and any change to its shape bumps the version

`tia-tools/gmks-hif-final-stats` (a page telling H.I.F. players whether a 選抜試験メモリー can still reach S5) needs this site's card data live, not as a copy, because new support cards enter decks the day they release (its own ADR 0001). Its Worker fetches `https://gakumas-supportcards.tia.run/data/cards.v1.json` server-side and caches it for an hour. So `bun run build` writes `dist/data/cards.v1.json` from the same generated modules the page bundles (`data/card-data-file.ts`, written by a build-only plugin in `vite.config.ts`). It holds `formatVersion`, `levelLimits`, `cards` (every card in `CARDS` as generated, held cards included) and `held` (the `HeldCard` list, each card with the reasons it is hidden). Deterministic like the other generated files, it is not committed. Every deploy rebuilds it, so it is exactly as current as the page. The unattended update deploys whenever its data pull request has merged into `main` (`update-data.yml`: the merge step sets the job output `merged` when `gh pr merge` succeeds or, after its retries, GitHub reports the pull request merged, and job `deploy` runs on `!cancelled() && needs.update.outputs.merged == 'true'`), also when a later step of the update fails (the `held-cards` issue, the merge back into `develop`). A cancelled run does not deploy, even after its merge: a cancel is a person stopping the run, and `always()` would make that deploy unstoppable; `notify` reports the cancel and `deploy.yml` can be dispatched by hand. Before this change the deploy waited for the whole `update` job to succeed, so such a failure left the new data on `main`, page and file alike, undeployed until the next deploy; a Codex review found that on 2026-10-29, and the user chose to close it here.

The file carries the engine's own types as they are, not a shape kept separately for publication: `Card`, `ClassifiedEffect`, `ParsedTrigger`, `ItemGrant`, `LevelLimits` and `HeldCard` in `src/engine/types.ts`, with the types they reference (`Breakpoint`, `FilterRef`, `ConditionRef`, `FilterFamily`, `Stat`, `CardType`, `Rarity`, `Plan`, `EffectKind`). The consumer copies them verbatim and rejects a format version it does not know. **Any change to the file's shape, including a change to any of those types, bumps `CARD_DATA_FORMAT_VERSION` in `data/card-data-file.ts`.** The file name carries the version (`cards.v2.json` next), so a new format can be published beside the old one while the consumer moves over. A deploy replaces the whole of `dist/`, so the old file stays on the site only while the build still writes it; coordinate a bump with that repository. The price: the engine's types can no longer change freely, since a change to them is now also a change to a published interface. Publishing a held card's data is not at odds with ADR 0005, which is about numbers this site shows: the file carries the game's data and no score. The consumer marks a held card's uncounted abilities as 「未計上」, with points the player fills in (its decision G12). Two details matter to a reader. An effect this site cannot read is left out of its card. An effect it can read, but for which some route profile has no number, stays in the card. Rejected: the consumer vendoring a copy with a sync script (it goes stale the day a card releases, per that repository's ADR 0001); committing the JSON (a second 1.5 MB copy of the generated data in git that could drift from the modules; building it from them means it cannot).

Source: requested by the coding-agent session of `tia-tools/gmks-hif-final-stats` working its Milestone 2 (`docs/plans/EXECPLAN_HIF_FINAL_STATS.md` in that repository, decisions G5, G12, G21), 2026-10-29, on the user's behalf; the format-version rule is as that request stated it; not yet reviewed by the user beyond that. Evidence: `data/card-data-file.test.ts` pins that the text parses back to exactly `CARDS`, `HELD` and `LEVEL_LIMITS` (a held card with its reasons from a fixture, since none is held today), that the path is `data/cards.v1.json`, and that the real Vite build, run in memory, writes exactly that text there; two builds wrote byte-identical files (210 cards, 0 held) equal to `cardDataJson` over the generated modules; the score snapshot check reported 0 unexplained moves.

Addendum 2026-10-31 (status unchanged, a second file under the same rule): the build also publishes `dist/data/skillcards.v1.json`, at `https://gakumas-supportcards.tia.run/data/skillcards.v1.json`, for `tia-tools/gkms-memomemo` (a memo of the produce memories a player owns, whose decisions D21, D22 and D42 have it read skill card data and art from this site at runtime). It holds `formatVersion`, `idols` (the playable P-idols in the game's order), `cards` (every skill card that can be a produce memory, one entry per id and upgrade level 0 or 1) and `hifAbilities` (each H.I.F. memory ability with its card). It follows the same rules as `cards.v1.json`: `bun run generate` writes the committed module `data/skillcards.generated.ts`, a build-only plugin writes the file from it, and any change to its shape bumps `SKILLCARD_DATA_FORMAT_VERSION` in `data/skillcard-data-file.ts` and with it the file name. Two things differ. The version is its own constant, because the two files have different consumers and change for different reasons. And its types live in that module with no imports, not in `src/engine/types.ts`, so the consumer copies one self-contained file. Release is decided when the generator runs, with the clock passed in: a card is in the file when its `viewStartTime` is `"0"` or not later than that moment, so the committed module is exactly what is published and what the image pipeline may publish art for. Anything the skill card builder cannot represent stops `bun run generate` before it writes any file, support cards included. Source: issue #65 and `docs/plans/EXECPLAN_SKILLCARD_DATA_AND_ICONS.md`, decisions K2 (the user's), K4, K5 and K8. Evidence: on `vertesan/gakumasu-diff` at `fc6afb8b5ba4`, the generator wrote 13 idols, 181 cards at level 0 and 180 at level 1, and 115 H.I.F. abilities, the counts gkms-memomemo's plan predicted; `data/skillcard-data-file.test.ts` pins the round trip, the path and the in-memory build; a second run was byte-identical.
