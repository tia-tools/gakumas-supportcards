# CLAUDE.md

This file provides guidance to a coding agent when working with code in this repository.

## Central Configuration

This template carries only the project-scoped scaffold: this CLAUDE.md skeleton, `docs/PLANS.md` (ExecPlan methodology), and `docs/adr/README.md` (ADR convention). Cross-project rules and the generic workflow skills (`grill-me`, `close-out`, `codebase-design`, `adopt-from-sibling`, `harvest-session`, `backlog`) live in the central `Taka499/claude` repository, deployed user-level at `~/.claude` — do not copy them into projects.

`docs/PLANS.md` is the one document that exists in both places. The canonical copy is `docs/PLANS.md` in `Taka499/claude`; the copy here is downstream and is checked in so a plan stays followable from a fresh clone with no `~/.claude`. Change the canonical one and propagate; see the note at the top of the file.

## Documentation

Project documentation lives in `docs/`. When creating or updating plans, ExecPlans, or design docs, save them there. Reference existing docs in `docs/` for context on project phases and milestones.

Every document should be self-sufficient: the reader should never need to hunt for context. Explain concepts inline. When a concept is already defined in another checked-in document, you may reference it by file path and section rather than repeating it — but the reference must be precise enough that the reader can find it immediately (e.g., "see `docs/PLANS.md` § Milestones"), not vague ("see the architecture doc").

## ExecPlans

When writing complex features or significant refactors, use an ExecPlan (as described in `docs/PLANS.md`) from design to implementation. ExecPlans are the persistence layer for cross-session development — they carry forward all context, decisions, and progress so that a fresh session can continue the work without loss. Completed plans are immutable history; when one finishes, run the close-out ritual (`close-out` skill) to extract its durable decisions before moving on.

- `docs/adr/0009-p-items-are-adjusted-per-item-and-their-cross-card-effects-enter-the-route-profile.md` — **accepted**: a P-item's fires are capped per item (an extra minimum on that item's effects, never a raise, under the lesson split in force), and an item that grants P-drinks is counted for the deck, not its card — a ticked item adds fires × drinks per fire to the run's Pドリンク獲得 count that every card is scored against, while the granting card's own 点数 does not change; items that grant skill cards are left out.

## Project Overview

A static web page for 学園アイドルマスター players showing the サポカ凸別点数一覧: every support card as a row, its 点数 at 凸0 through 凸4 as columns, with a thumbnail that reveals the card name on hover, filterable by card type, plan and rarity. Points measure expected parameter gain over one run of a scenario (per `docs/adr/0001`, whose 2026-09-29 addendum makes the パラメータボーナス base follow the player's 選抜試験 score share, default main 2 : sub 7 : other 1), and the published scenario is H.I.F. (『Hatsuboshi IDOL FESTIVAL』), taken end to end first as the tracer bullet; 初LEGEND exists in the code and under test as the second scenario but is not published, because its route counts are still guesses, and the route sheet that would replace them is dropped for now (per `docs/plans/EXECPLAN_SUPPORT_CARD_SCORE_TABLE.md` decisions D38, D39, D44 and `docs/adr/0005`). Scenarios are data files, not code, so a new game scenario is a new file (per `docs/plans/EXECPLAN_SUPPORT_CARD_SCORE_TABLE.md`). How often an effect fires is counted by occasion, filters and conditions (per `docs/adr/0004`; `docs/plans/EXECPLAN_COUNTING_MODEL.md`, complete 2026-09-22 — the migration moved no score across 204 cards × 4 route profiles × 凸0–4, and a replay of the 2026-09-20 data update passes the stability check). Card data is generated daily from the `vertesan/gakumasu-diff` YAML dump (per `docs/plans/EXECPLAN_SUPPORT_CARD_SCORE_TABLE.md` decision D46); the app is deployed as a Cloudflare Worker under the tia-tools organisation at its own tia.run subdomain, with an in-app feedback form posting to the private `tia-tools/feedback` repository (same plan, decisions D7–D8). That plan, `docs/plans/EXECPLAN_SUPPORT_CARD_SCORE_TABLE.md`, is complete (2026-09-28): all seven milestones accepted, the last by the user's line-by-line confirmation of the ten golden breakdowns (38 of 38 lines); the update's pull-request path has not yet run on a real upstream change (its § Outcomes & Retrospective). `docs/plans/EXECPLAN_SCORE_ADJUSTMENTS.md` is complete (2026-09-29): its four milestones — the 「SP」 badge and facet, the 選抜試験 score-share slider with the snapshot in parts, the 「Pアイテム」 panel with per-item caps and deck drinks, and the item icons — plus five post-release refinements of that panel were released as PRs #14, #17, #19, #21, #23 and #25 and verified on the site; each milestone was reviewed by Codex to LGTM after fixes (per `docs/adr/0009` and the 2026-09-29 addenda of `docs/adr/0001`, `0003` and `0006`).

## Architecture

- `scripts/` — the Bun generator `generate-cards.ts` over `scripts/lib/` (tables loader, trigger parser, effect-type audit, card builder, emitters); it writes the committed `data/*.generated.ts` (per `docs/plans/EXECPLAN_SUPPORT_CARD_SCORE_TABLE.md` Milestone 1). `scripts/lib/parse-trigger.ts` reads a trigger id as occasion, filters and conditions, and every generated effect carries the result as `trigger`; `scripts/lib/effect-types.ts` lists which effect types are parameter gains and which are audited as none (per `docs/adr/0004` and `docs/plans/EXECPLAN_COUNTING_MODEL.md` Milestones 1–3).
- `data/` — generated cards, level limits and `held.generated.ts` (cards the table must not show because an effect cannot be counted, per `docs/adr/0005`; the page leaves these cards out) and `scores.generated.json` (the parts of every other card's published score that a data update can move — flat points per route profile and lesson-split preset, and パラメータボーナス+ permil per 凸; the bonus base is applied when a score is read, so a base or share change leaves the file untouched — the baseline of `scripts/check-score-stability.ts`; per `docs/adr/0006`, addendum 2026-09-29); `data/scenarios/` (one file per scenario with its route profiles — occasions, filters, optional conditions, lesson splits and the パラメータボーナス base — plus golden and real-data tests).
- `src/engine/` — pure scoring engine (`score.ts`, `count.ts`, `share.ts`, `types.ts`), no DOM, dependencies passed in. `share.ts` maps a stat to its role in a lesson split (main / sub / other) and to its share of the 選抜試験's distributed rewards under the player's `AuditionShare` (tenths, default 2:7:1), which `parameterBonusBase(lessonsOfStat, auditionShare)` turns into the パラメータボーナス base (per `docs/adr/0001`, addendum 2026-09-29). `count.ts` turns an effect's trigger into occurrences per run: the occasion's count, narrowed by each filter (the lesson-stat filter by the lesson split, the others by the profile) and by each condition the profile states, capped by the effect's own cap, and 0 when the trigger belongs to another scenario (per `docs/adr/0004`).
- `scripts/images/` — Python (uv) image pipeline: `extract.py` downloads card art and the icons of the P-items cards grant through a pinned, gitignored GkmasObjectManager checkout and writes, per file, a lossless master and the served rendition — a 192 × 108 webp thumbnail per card, a 48 × 48 webp icon with transparency per item (`img_general_pitem_{r}-{nnn}.webp`, no reshape); `upload.py` sends the ones the deployed site lacks to R2, master first; rules live in pure tested modules (`thumbnail.py`, `decode.py`, `uploads.py`). Setup, commands and the reasons are in `scripts/images/README.md` (per `docs/adr/0003` with its 2026-09-29 addendum for the icons, and first-plan decisions D30–D32, D35).
- `infra/worker/` — the Cloudflare Worker for `gakumas-supportcards.tia.run`: static assets from `dist/` plus `/img/w192/*` card thumbnails and `/img/w48/*` P-item icons from the R2 bucket `tia-assets`, whose `master/` prefix it never serves (`img.ts`, `worker.ts`, `wrangler.toml`), and `POST /feedback`, which turns the page's feedback form into an issue in the private `tia-tools/feedback` repository, at most 5 per client per day counted in KV (`feedback.ts`, with `feedback-contract.ts` shared by the page; per `docs/plans/EXECPLAN_SUPPORT_CARD_SCORE_TABLE.md` decisions D7, D42); deploy, feedback setup and verify steps in `infra/worker/README.md`.
- `src/app/` — the Preact page, entered from `index.html` → `src/main.tsx`: pure `url-state.ts` (view state ⇄ query string), `rows.ts` (score, filter, sort), `panel.ts` (the model of the 「カウントを調整」 panel: four fixed sections, filters and conditions nested under and bounded by what they narrow, inputs folded when no card in view reacts to them, and `applyOverrides`), `count-labels.ts` (Japanese names for occasions, filters and conditions, also used to word the breakdown) and `feedback.ts` (what the feedback form sends, with the current view and build attached), each with tests, and the components that render them (first plan Milestone 3; `docs/plans/EXECPLAN_COUNTING_MODEL.md` Milestone 3, decisions C6, C10, C18, C19). `item-panel.ts` is the model of the 「Pアイテム」 panel (`ItemPanel.tsx`, its own folded panel below 「カウントを調整」, decision A24; its explanation, the granting card with its thumbnail and the drinks arithmetic sit behind hover/tap hints from `Hint.tsx`, decision A26): one row per P-item of a card in view with a cap on its fires (`i.<itemId>`, an extra minimum the engine applies to that item's effects; the row's ceiling is the item's fires under the selected lesson split, or under 「カードごとに最適」 the preset that favours it — a Da-SP-lesson item fires 0 times under a split with no Da lessons, decision A25) and, for the ten drink-granting items, a 「有効」 switch (`d.<itemId>=1`) whose fires × drinks per fire are added to Pドリンク獲得 for every card through `applyOverrides`'s third argument and shown as a read-only, unbounded child of it stating the total, while the input keeps the player's own count; the three skill-card-granting items are a documented gap (per `docs/adr/0009`). `share.ts` and `ShareSlider.tsx` are the 「選抜試験のスコア配分」 control beside 「レッスン配分」: a two-thumb bar in tenths for the main, sub and other stat of the split, in the URL as `a=<main>.<sub>.<other>` (absent = 2.7.1; same plan, decision A5). Count overrides live in the URL as `o.<Occasion>`, `f.<Occasion>.<family>.<member>` and `w.<condition key>`; the facet 「SP発生率+」 (`sp=1`) keeps only cards flagged `spRate`, which also wear an 「SP」 badge in the card cell — the effect itself still scores 0 (per `docs/plans/EXECPLAN_SCORE_ADJUSTMENTS.md` Milestone 1, decision A2). The generated card data ships inline in the bundle (56 KB gzipped, first plan decision D28).

## Setup and Development

- Runtime and package manager: Bun. `bun install` installs the dev dependencies (`js-yaml`, `typescript`, type packages). Inside a sandbox that blocks `~/.bun`, run it as `BUN_INSTALL_CACHE_DIR="$TMPDIR/bun-cache" bun install`.
- Upstream game data is the `vertesan/gakumasu-diff` YAML dump. Scripts read each table from `.cache/gakumasu-diff/<Table>.yaml` when present and otherwise fetch `https://raw.githubusercontent.com/vertesan/gakumasu-diff/main/<Table>.yaml` and cache it there; `.cache/` is gitignored, delete it to force a refresh.

## Build and Test

- `bun run dev` — Vite dev server at `http://localhost:5173`; `bun run build` writes `dist/`; `bun run preview` serves it. Thumbnails resolve to `/img/*`: in production the Worker serves them from R2 (per `docs/adr/0003`); the dev server serves them from `scripts/images/out/w192` when the images have been extracted locally, and otherwise the cells fall back to the card name.
- `bun run generate` — runs `scripts/generate-cards.ts`, rewriting `data/cards.generated.ts`, `data/held.generated.ts`, `data/levelLimits.generated.ts` and `data/scores.generated.json` from the cached tables and the shipped scenarios. Output is deterministic (no timestamps), so a second run yields no diff. An effect that cannot be counted does not stop the run: its card is listed in `data/held.generated.ts` with the reason and the effect is left out of the card — a trigger piece of unknown kind (including an unknown `for_` scenario token), an effect type that is neither a parameter type nor audited as non-parameter, or a trigger that needs an occasion or filter number some shipped route profile lacks. The page shows only cards that are not held. A card whose level-1 skills include SP発生率+ is flagged `spRate: true` (the effect is still skipped, per `docs/adr/0001`). A card's granted P-items that have a countable stat effect or grant P-drinks are listed as `items` with the item's `fireLimit` and, for drinks, the quantity per fire read from the reward id (`…-02_02` = 2) and the trigger (per `docs/plans/EXECPLAN_SCORE_ADJUSTMENTS.md` decisions A9, A16). Exits 1 without writing when the dump itself looks broken: a schema error, an unknown enum value, item effect type or event reward resource, a dangling id, a skill that grants a P-item, an item reward set naming neither drink nor card or a reward quantity that is a range or missing, an SP発生率+ skill that appears only above level 1 (the badge would be wrong at 凸0; `docs/plans/EXECPLAN_SCORE_ADJUSTMENTS.md` decision A15), or a card count that would drop (`--allow-fewer` overrides the last). `GAKUMASU_DIFF_CACHE=<dir>` points the generators at another table directory.
- `bun scripts/check-score-stability.ts [--base <git ref> | --base-file <path>]` — the check that replaces a person reading a data update's diff (per `docs/plans/EXECPLAN_COUNTING_MODEL.md` decision C20): recomputes every published score's parts (flat points per profile and preset, bonus permil per 凸) from the working tree and compares with `data/scores.generated.json` as committed at the ref (default `HEAD`); exits 1 when a card whose generated record is unchanged scores differently, when the working tree's snapshot is stale, or when the committed file is in the former folded-totals format (named as such). A deliberate route-profile or engine change fails it by design: review the listed moves, then commit the regenerated snapshot.
- `.github/workflows/update-data.yml` — the unattended daily update at 11:30 JST (and by hand from the Actions tab): regenerates from fresh tables and, only after the tests, the type check, `bun run lint` and `bun scripts/check-score-stability.ts` pass, merges the data through a pull request, opens or refreshes the `held-cards` issue, merges `main` back into `develop` and deploys; images for new cards are best effort; a last job, `notify`, runs after the update and the deploy whatever happened and posts to the owner's Discord through Nudge (`Taka499/nudge/actions/notify`; an OIDC token, hence `id-token: write` on that job alone) when either did not succeed, data was published or the run was started by hand, and on Mondays even when nothing changed (same plan, decisions D41, D43, D46; `docs/adr/0005`, `docs/adr/0006`). `.github/workflows/deploy.yml` deploys every push to `main` that touches the page, data or Worker. `.github/workflows/check.yml` runs the tests, type check, lint, snapshot check and build on every pull request into `develop`, read-only. Every action is pinned to a full commit hash with a version comment, and `.github/dependabot.yml` proposes updates as one grouped pull request a week into `develop`; merging it is a person's decision (decision D47). Workflows cannot run locally: `scripts/lib/workflows.test.ts` pins their triggers, permissions, gate order, and that each action is an allowed one pinned to a hash, and `bun scripts/update-report.ts --pr-body <file> --issue-body <file>` prints what an update would say.
- `bun run type-check` — `tsc --noEmit` over `src/`, `scripts/`, `data/`, `infra/` and `vite.config.ts`.
- `bun run lint` — Oxlint with `oxlint-tsgolint` (type-aware) and `eslint-plugin-security` over every TypeScript file, configured in `oxlint.config.ts`; exits 1 on any finding, warnings included (`--deny-warnings`), and prints nothing on a clean run. Size, complexity and type escape hatches are errors (§ Code Style). A justified exception lives in `oxlint.config.ts` with its reason and removal condition, never as an inline disable comment (per `docs/adr/0007`; `docs/plans/EXECPLAN_OXLINT.md`, complete 2026-09-28, decisions O2, O3). A gate in `deploy.yml`, `check.yml` and `update-data.yml`.
- `uv run pytest` in `scripts/images/` — hermetic tests of the image pipeline rules (naming of card art and item icons, thumbnail and icon format, item master without reshape, Unity-version fallback, upload planning per rendition, released-cards-only); needs `uv sync` first, no network and no vendored checkout.
- `bun test` — unit tests, co-located as `*.test.ts`: the Worker's image handler against a fake bucket (`infra/worker/img.test.ts`), generator rules against small fixtures (`scripts/lib/`), the scoring engine against fixture cards (`src/engine/score.test.ts`, `src/engine/count.test.ts`), the panel model and URL state (`src/app/`), a real-data check that every shipped route profile names every occasion and filter the generated cards use (an omitted one would silently score 0, so 0 must be written), keeps every filter and condition count within its occasion, and scores all cards finitely (`data/scenarios/scenarios.test.ts`), and golden scores over frozen copies of ten cards, so a game rebalance cannot fail them (`data/scenarios/golden.test.ts` with `golden.snapshot.ts`, per `docs/plans/EXECPLAN_COUNTING_MODEL.md` decision C8).

## Code Style

- Enforced by `bun run lint` (per `docs/adr/0007`; `docs/plans/EXECPLAN_OXLINT.md`, complete 2026-09-28, carrying out `docs/plans/EXECPLAN_SUPPORT_CARD_SCORE_TABLE.md` decision D45): a function has at most 60 lines (120 in `*.test.ts`), cyclomatic complexity 15, blocks nested 4 deep, callbacks nested 4 deep and 6 parameters; no `any`, no `x!`, no `x as T` (`as const` is fine — use a type guard or a value typed correctly from the start), no promise handed to a `void` callback or left unhandled, no empty `catch`; the `security/*` rules are on, with file reads by path allowed only in `scripts/` and `vite.config.ts`. A test that reaches into a fixture uses a throwing helper (`must(value, what)`) rather than `!`.

## Commit Discipline

- Follow Git-flow: `main` is production and `develop` is development (per `docs/adr/0008`; `docs/plans/EXECPLAN_SUPPORT_CARD_SCORE_TABLE.md` decision D40). Branch features from `develop` and merge them back with merge commits; a release is a merge of `develop` into `main`. Merging into `main` deploys the site (`.github/workflows/deploy.yml`), so nothing unfinished goes there. The daily data update is the only thing that enters `main` directly, and it merges `main` back into `develop` afterwards.
- Use small, frequent commits rather than large, infrequent ones
- Only add and commit affected files; leave untracked files as they are
- Never add coding agent attribution in commits
